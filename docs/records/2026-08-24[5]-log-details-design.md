# Окно деталей лога (LogDetails)

> **Состояние на 2026-08-24:** спека согласована с владельцем, к реализации
> не приступали.
> **Что это:** устройство и API нового экрана с полным описанием одного
> лога, включая дерево `data` с переключением view/hidden на реальные
> значения.
> **Связанные записи:** нет.

## Задача

Пункт из `docs/backlog.md`: «Полноценный вывод информации по конкретному
логу: раскрытие всех вложенных данных». Формулировка владельца: по нажатию
на лог открывается окно с полным описанием лога, включая `data`, с
возможностью переключения данных из `view` и `hidden` в реальные.

Сейчас тап по логу ничем не обрабатывается: `LogItem` принимает `onTap`, но
`Logs` его не передаёт — только `onTapDown: controller.pause`
(`lib/src/logs.dart:965`). `LogItem` ограничивает вывод по высоте
(`maxLines: 3` для сообщения, `8` для данных и стека), а `hidden`-свойства
и реальные значения под `view` не показывает в принципе — их не отдаёт
`Loggable.objectToString`.

## Что даёт team_logger

Пакет — UI-надстройка, вся модель данных приходит из `team_logger` 0.7.0.
Существенное для этой работы:

- `LoggableData.props` — публичный список `Prop`. У `Prop` публичны `name`,
  `value`, `view`, `showName`, `hidden`, `config`, а также `toLogString()` и
  `toMapEntry()`.
- `hidden` задокументирован как «не печатается `objectToString`, **но может
  быть показан в пользовательском интерфейсе**» — библиотека прямо
  рассчитана на такого потребителя.
- `computed` задокументирован как «должен быть опущен в интерфейсе,
  показывающем реальные данные». Публичного признака у него нет: `computed`
  кладёт в `value` экземпляр приватного `_ComputedProp`.
- `Prop.noView` / `LoggableNoView` публичны — «есть ли view» проверяется
  публично.
- `LoggableView.toLogString(value, {theme, depth})` публичен — view с
  собственным конвертером рисуется напрямую.
- `LogTheme.depthTheme(depth)` даёт цвета вложенности, те же, что в консоли.
- Получить структуру: `Loggable.logClassInfo()`, `LoggableData.props`,
  `LoggableWrapper.data`/`.config`, `LoggableMultiData.data`/`.config` —
  всё публично.

Чего team_logger не даёт (границы возможного, см. «Ограничения»):
реестр `registerTypeConverter` приватен; `SanitizeContext` имеет только
приватный конструктор; `Loggable._withSegment`/`_sanitizeChild` приватны.

## Принятые решения

Развилки и выбор владельца:

1. **Форма подачи `data` — интерактивное дерево** с раскрытием узлов, а не
   полный текст простынёй. Ровно то, что записано в бэклоге.
2. **Переключатель — один тумблер на окно**, два режима целиком: «как в
   логе» и «реальные данные». Не два независимых флага и не переключение
   по отдельным свойствам.
3. **`Loggable.sanitizer` в режиме «реальные данные» не соблюдается.** Окно
   читает объекты из памяти, как инспектор в отладчике; режим по
   определению снимает всё, что прячет значение. Полумеры («уважать
   насколько позволяет публичное API») отвергнуты: защита получилась бы
   дырявой и непредсказуемой — для одних правил работает, для других молча
   нет. Требует явного предупреждения в README и правки формулировки в
   доках team_logger («ALL outputs: publishers, an in-app log viewer,
   session export»).
4. **`computed` показываются всегда и помечаются** отдельным цветом, а не
   опускаются, как предлагает документация team_logger.
5. **По тапу открывается полноэкранный route.** Не диалог и не адаптивный
   выбор формы.
6. **Копирование в буфер в эту работу не входит** — отдельным пунктом в
   `docs/backlog.md`.
7. **Устройство — модель узлов плюс плоский виртуализированный список.**
   Раскрытая коллекция на десятки тысяч элементов должна работать.

## Публичный API

`lib/flutter_team_logger.dart` начинает экспортировать третий виджет:

```dart
class LogDetails extends StatefulWidget {
  final Log log;
  final LogTheme theme;
  const LogDetails(this.log, this.theme, {super.key});
}
```

Позиционные `log` и `theme` — как у `LogItem(log, theme)`. `theme` — уже
выбранная под уровень лога `LogTheme`, не `LogMainTheme`.

Виджет — экран целиком: `Theme(_theme) → Scaffold → AppBar` по образцу
`Logs` (`lib/src/logs.dart:336-346`), с той же тёмной `ThemeData`. Как и
`LogItem`, он не знает, как его показали, и годится для вставки в свой
диалог или панель.

`Logs` по тапу делает `Navigator.push`, передавая
`controller.widget.theme[log.level]`. `onTapDown: controller.pause`
остаётся: список сначала встаёт на паузу, потом открывается окно.

## Модель узлов

Один класс, а не иерархия из пяти: различия между свойством, секцией,
элементом коллекции и записью `Map` сводятся к виду метки.

```dart
enum LogNodeKind { root, prop, section, index, entry }

final class LogNode {
  final LogNodeKind kind;
  final String? name;        // имя свойства, ключ секции/Map, индекс
  final bool showName;
  final Object? value;       // реальное значение (Prop.value)
  final Object? view;        // Prop.noView, если нет
  final bool hidden;
  final bool computed;
  final LoggableConfig config;
  final int depth;
}
```

Корневой узел строится из `log.data`, дальше — рекурсия.

### Признак computed

Все `computed`-свойства кладут в `value` один и тот же const-инстанс
приватного `_ComputedProp`. Достать его можно публичным API — зондом:

```dart
final _computedMarker =
    (Loggable.mapBuilder()..computed('probe', 0)).props.first.value;
```

Дальше `identical(prop.value, _computedMarker)` — точный признак, без
эвристик на строку `<computed>` и без правки team_logger. Зонд считается
один раз, лениво.

Риск: сломается, если team_logger перестанет использовать общий
const-инстанс. Тогда все `computed` просто перестанут помечаться —
поведение деградирует, а не падает.

### Раскрытие

Цель разбора зависит от режима: «как в логе» разбирает то, что реально
печатается (`view`, если он задан и не является `LoggableView`), «реальные
данные» — всегда `value`.

| цель | дети |
|---|---|
| `LoggableWrapper` | прозрачен: рекурсия в `.data` с `.config.merge(...)` |
| `Loggable` | `logClassInfo().props` → узлы `prop` |
| `LoggableData` | `.props` → узлы `prop` |
| `LoggableMultiData` | `.data.entries` → узлы `section` |
| `Map` | записи → узлы `entry` (ключ может быть объектом) |
| `Iterable` | элементы → узлы `index` |
| прочее | лист |

Дети строятся лениво, по факту раскрытия узла.

### Рендер значения

Точная копия ветвления `Prop.toLogString`
(`loggable_data.dart:591-624`) минус приватные сегменты санитайзера, от
которых мы отказались решением 3:

```dart
switch (real ? Prop.noView : view) {
  LoggableNoView() =>
      Loggable.objectToString(value, theme: theme, depth: depth + 1, config: config),
  final LoggableView v =>
      theme.formatValue(v.toLogString(value, theme: theme, depth: depth),
          escapeAnsiCodes: false),
  final v =>
      theme.formatValue('$v${Loggable.unitsToString(config.resolvedUnits, theme)}',
          escapeAnsiCodes: false),
}
```

Имя узла рисуется `theme.data.keyStyle`, двоеточие —
`theme.depthTheme(depth).punctuation`, как в консоли. Результат — ANSI-текст,
он идёт в `TextSpan` через существующий `ansi_utils.dart`.

Свёрнутый раскрываемый узел показывает ту же краткую сводку, что и
консоль (`User(…)`, `[₌₃ …]`).

### Лимиты не трогаем

`collectionMaxCount` и `collectionMaxStringLength` применяются только
внутри коллекций (`iterableToString`, `mapToString` и соседи); к
строке-листу они не применяются вовсе (`_stringToString`,
`loggable.dart:2320`), так что длинные строки и так печатаются целиком.
Коллекции мы перечисляем узлами дерева сами, минуя лимит, а в свёрнутом
виде сводка с лимитом полезна. `Loggable.forceConfig` задокументирован как
«то, что вызов не может поднять» — перебивать его нельзя. Конфиг
наследуется по дереву как есть, никакого «снятия лимитов» в коде нет.

Следствие, которое стоит понимать: раскрытая коллекция показывает все
элементы, в том числе за пределом `collectionMaxCount`. Это согласуется с
решением 3 — окно является инспектором.

### Плоский список

Раскрытые узлы уплощаются в один список и рендерятся `ListView.builder`.
Состояние раскрытия живёт в контроллере экрана, а не в виджетах узлов: оно
переживает переключение тумблера и перестроение.

Узел опознаётся путём от корня — последовательностью меток
(`имя свойства` / `ключ` / `индекс`). Путь строится по позиции в структуре,
а не по объекту-значению: иначе одинаковые значения на разных ветках
раскрывались бы вместе, а перестроение дерева после смены режима теряло бы
состояние.

## Режимы и пометки

| | как в логе | реальные данные |
|---|---|---|
| свойство с `view` | рисуется `view` | рисуется `value` |
| `hidden` | строки нет | строка есть, бейдж `hidden`, имя стилем `dim` |
| `computed` | рисуется `view` | значение `<computed>`, бейдж `computed`, стиль `emphasis` |
| `Loggable.sanitizer` | как в логе | не применяется |
| раскрытие узла | разбирается `view` | разбирается `value` |

Режим по умолчанию — «как в логе».

Цвета берутся из `LogTheme`, свои не изобретаются: `theme.data.dim` для
`hidden`, `theme.data.emphasis` для `computed`. `theme.main.hiddenStyle`
для пометок **не годится** — это `Style(invisible: true)` для консольных
заполнителей, в UI такой текст был бы буквально невидим.

## Состав экрана

Сверху вниз, всё без ограничений по высоте, в отличие от `LogItem`:

1. Шапка: уровень, время, путь, `#num`, traceIds, теги.
2. Сообщение.
3. Дерево `data`: раскрыт первый уровень — секции `LoggableMultiData`,
   свойства `Loggable`/`LoggableData`, элементы коллекции; глубже — по
   тапу. Если `data` — лист, дерева нет, есть одна строка значения.
4. `error` и стек-трейс через тот же `LogStackTrace`, что и `LogItem`.

Шапку рисует `_BorderContainer`, сейчас приватный в `log_item.dart`. Он
переезжает в `lib/src/uikit/` (рядом с `chip.dart`) и используется обоими
экранами — точечная правка по месту работы, не отдельный рефакторинг.

## Поведение в углах

- Лог удалён из `LogStorage`, пока окно открыто: окно продолжает работать,
  объект `Log` на руках у виджета.
- Дерево ленивое, поэтому мутабельный объект показывает состояние на момент
  раскрытия узла, а не на момент записи лога. Для инспектора это верно, но
  в dartdoc `LogDetails` это надо сказать явно.
- `data` может быть чем угодно: `LogNoData` (тогда блока данных нет),
  примитив, коллекция, `LoggableMultiData`, `Loggable`. Корень
  обрабатывается тем же разбором, что и любой узел.
- Пустой `message`, отсутствующие `error`/`stackTrace`/`tags`/`traceIds` —
  соответствующие блоки не рисуются, как в `LogItem`.

## Ограничения

1. **Объекты с зарегистрированным `Loggable.registerTypeConverter` не
   раскрываются.** Реестр конвертеров в team_logger приватен, прочитать его
   нечем. Такие объекты становятся листьями: текстом они рисуются
   правильно (конвертер применится внутри `objectToString`), но развернуть
   их по свойствам нельзя. В `example/` кастомные конвертеры есть, так что
   это будет видно. Лечится публичным геттером в team_logger — отдельная
   работа.
2. **Dart records не раскрываются** — публичного способа перечислить их
   поля нет. Лист. В `example/lib/data.dart` запись `(12, 'abc', true,
   null)` присутствует.
3. **`sanitizer` в режиме «реальные данные» не действует** — решение 3.
4. **Путь sanitizer'а теряется** и в режиме «как в логе»: узлы дерева
   рендерятся по одному, вне общего обхода, поэтому правила по `path`
   (`user.card.number`) не воспроизводятся. Ещё одна причина, по которой
   полумеры из решения 3 были бы обманом.

## Версия и публикация

Minor-версия пакета следует за minor-версией team_logger
(`docs/conventions.md`), team_logger остаётся 0.7.0 — значит это **0.7.1**.

Публикация в эту работу не входит: по `AGENTS.md` она требует отдельного
разрешения владельца, состоящего только из просьбы опубликовать.
