# AGENTS.md

Точка входа для AI-агента (Claude Code, Codex) в этом репозитории.
`CLAUDE.md` в корне — это просто ссылка `@AGENTS.md`, все правила живут здесь
одним файлом на оба агента.

Сессия может оборваться в любой момент без предупреждения. Это нормальный
режим работы, а не авария — весь смысл файлов в `docs/` в том, чтобы новая
сессия могла восстановить контекст без участия владельца.

## С чего начать в новой сессии

1. Прочитать этот файл целиком.
2. Прочитать `docs/handoff.md` — текущее состояние проекта. Единственный
   источник правды о том, что происходит прямо сейчас.
3. Прочитать `docs/backlog.md` — пожелания владельца, ещё не взятые в работу.
   Если что-то оттуда можно сделать — предложить владельцу.
4. По необходимости — `docs/architecture.md` (устройство) и
   `docs/conventions.md` (конвенции кода и репозитория).

## Карта docs/

- `docs/handoff.md` — текущее состояние проекта. Держать всегда актуальным:
  обновлять при каждом значимом изменении состояния. Не пересказывать здесь
  историю коммитов и не разбирать законченные эпизоды работы — это
  `docs/records/`. Пожелания владельца тоже не сюда — это `docs/backlog.md`.
- `docs/backlog.md` — пожелания владельца. Пишет только владелец, агент туда
  не пишет. Агент читает, следит за списком, предлагает взять пункт в работу.
  Если пункт взят и выполнен — агент сам удаляет его из файла.
- `docs/architecture.md` — устройство проекта: то, что меняется редко. Не
  хранить здесь то, что часто меняется (текущее состояние — в
  `docs/handoff.md`).
- `docs/conventions.md` — конвенции кода и репозитория.
- `docs/records/` — история: спеки, планы, отчёты, ревью.

## Git

- Мержить прямо в `main`, без PR.
- Не коммитить чужие правки вместе со своими. Если в дереве обнаружено
  незнакомое состояние (файлы, ветки, незакоммиченные правки) — сначала
  разобраться, чьё это и почему оно там, и только потом коммитить или
  затирать.

## docs/records — история правок

Спеки, планы, отчёты, ревью — сюда, а не в стандартные пути скиллов (например
`superpowers:writing-plans` по умолчанию пишет в `docs/superpowers/plans/` —
итоговый документ всё равно кладётся в `docs/records/` по схеме ниже, второй
копии не оставлять).

Имя файла: `YYYY-MM-DD[N]-name-kind.md`. Квадратные скобки — литералы, то
есть в реальном имени файла есть символы `[` и `]`. `N` — порядковый номер
записи за этот день (считать заново с 1 каждый день). `kind` — последнее
слово перед `.md`, тип документа:

- `plan` — план работ.
- `design` — устройство и API.
- `report` — отчёт о сделанном: о волне правок, о разборе дефекта, о
  предмержевом ревью одной работы.
- `project-review`, `architecture-review`, `flutter-review`, `bug-hunter`,
  `performance-review` — полное ревью всего проекта глазами ревьюера
  (состояние всей кодовой базы), а не итог одной работы. Эти пять слов
  соответствуют одноимённым скиллам.

Если подходящего слова нет — взять своё, но по тому же принципу: одно слово о
жанре записи, а не о теме.

Каждый файл в `docs/records/` начинается с шапки о текущем состоянии этой
записи (дописывается и обновляется по мере того, как меняется судьба
работы — сделано и смержено, брошено, частично сделано, пересмотрено позже):

```markdown
> **Состояние на YYYY-MM-DD:** что с этой работой сейчас — сделано и
> смержено (коммит), брошено, частично сделано, пересмотрено позже.
> **Что это:** одна фраза о содержимом.
> **Связанные записи:** имена других файлов в `docs/records/`.
```

### Ревью и вердикты

При работе с ревью (разбор находок из `project-review`, `bug-hunter` и т.п.)
в конец каждой находки дописывается вердикт по этой находке — отдельным
абзацем, прозу самой находки при этом не трогать. На одну находку — не больше
одного вердикта.

## Язык

Документы для владельца и агентов (`AGENTS.md`, `docs/*.md`, `docs/records/`)
и общение с владельцем — по-русски.

Публичные артефакты — по-английски: `README.md`, `CHANGELOG.md`,
dartdoc-комментарии в `lib/`, сообщения коммитов, тексты ошибок.

## Публикация на pub.dev

Публикация на pub.dev — это вся связка целиком: коммит `Release X.Y.Z`, тег
`vX.Y.Z`, push и `dart pub publish`, одним заходом и подряд. Ни одну часть по
отдельности. Подготовку к публикации делай свободно — это обычные правки в
дереве, их можно откатить.

Разрешение на публикацию — только явное и только на эту связку. Оно не
переносится на следующий релиз, не наследуется от прошлого раза и не
выводится из готовности релиза. «Всё готово к публикации» — не разрешение.
Пройденный чеклист — не разрешение. Связка — отдельная задача. Если в
сообщении владельца есть хоть что-то ещё, кроме публикации, — не запускать
ничего из связки, даже если слово «публикуй» стоит в нём прямым текстом. Не
спрашивай — откажи. В таком случае не задавай вопроса «публиковать?», не
предлагай вариантов и не выноси решение на подтверждение. Сделай остальную
работу и откажи в публикации, назвав условие: разрешение должно прийти
отдельным запросом владельца, состоящим только из просьбы опубликовать.
Сомневаешься — не публикуй. Отказ стоит одного сообщения, ошибка стоит номера
версии.
